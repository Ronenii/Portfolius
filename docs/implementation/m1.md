# M1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Supabase authentication, a first-run profile wizard, and manual holdings CRUD so a signed-in user can create portfolio data scoped to their own Supabase user ID.

**Architecture:** The frontend owns Supabase session management and sends the access token to the FastAPI API. The backend verifies Supabase JWTs, enforces user scoping on every protected route, and persists profile, instrument, and holding records through SQLAlchemy repositories. M1 avoids portfolio math, price refresh, charts, AI, and market-data integrations.

**Tech Stack:** FastAPI, SQLAlchemy, Alembic, PyJWT, pytest, React, Vite, TypeScript, Supabase JS, TanStack Query, React Router, Vitest.

---

## M1 Scope

Included:

- Add Supabase JWT verification on protected backend routes.
- Add Alembic schema for `profiles`, `instruments`, and `holdings`.
- Add backend profile API: `GET /api/v1/profile` and `PUT /api/v1/profile`.
- Add backend holdings API: `GET/POST /api/v1/holdings` and `GET/PUT/DELETE /api/v1/holdings/{holding_id}`.
- Add deterministic user scoping for all profile and holdings queries.
- Add frontend Supabase client and auth UI for Google OAuth plus magic-link email.
- Add frontend routing and an authenticated app shell.
- Add first-run profile wizard.
- Add manual holdings list/create/edit/delete flow.
- Update local environment examples and README setup notes.

Excluded:

- Market-data lookup, yfinance, and Financial Modeling Prep integration.
- Portfolio snapshots, allocation breakdowns, and charts.
- Assistant conversations or LLM calls.
- Transactions, CSV import, target allocations, and projections.
- Supabase Row Level Security policies for app tables; M1 relies on backend JWT verification and user-scoped queries because app tables are managed through FastAPI.

## Definition of Done

M1 is complete when:

- Unauthenticated requests to protected backend routes return `401`.
- Authenticated profile and holdings API tests pass with fake Supabase JWTs.
- User-owned backend records are always filtered by the authenticated `user_id`.
- Alembic upgrades a clean database to include M1 tables.
- The frontend can sign in with Google OAuth or magic-link email through Supabase.
- A signed-in user without a profile is routed to the profile wizard.
- A signed-in user with a profile can create, edit, list, and delete holdings.
- Frontend tests cover API token headers and key auth/profile/holdings states.
- Backend and frontend lint, tests, and production build pass.
- README and `.env.example` files match the actual setup.

## Step 3: Backend Profile API

Goal: add authenticated profile read and upsert behavior.

Files:

- Create: `backend/app/schemas/__init__.py`

- Create: `backend/app/data/repositories/__init__.py`

- Create: `backend/tests/conftest.py`
- Create: `backend/tests/test_profile_api.py`

API contract:

```text
GET /api/v1/profile
401 unauthenticated
404 authenticated but no profile
200 profile for authenticated user

PUT /api/v1/profile
401 unauthenticated
200 created or updated profile for authenticated user
```

Request body:

```json
{
  "display_name": "Ronen",
  "base_currency": "USD",
  "time_horizon": "10+ years",
  "investment_frequency": "monthly"
}
```

Response body:

```json
{
  "id": 1,
  "user_id": "supabase-user-id",
  "display_name": "Ronen",
  "base_currency": "USD",
  "time_horizon": "10+ years",
  "investment_frequency": "monthly",
  "created_at": "2026-06-04T00:00:00Z",
  "updated_at": "2026-06-04T00:00:00Z"
}
```

Implementation:

- Keep `user_id` server-owned; ignore any client attempt to set it.
- Validate `base_currency` as a three-letter uppercase currency code.
- Trim profile text fields and reject empty values.
- Use repository functions for `get_profile_by_user_id()` and `upsert_profile()`.
- Use test overrides for auth and database sessions in `tests/conftest.py`.

Test cases:

- `GET /api/v1/profile` requires auth.
- `GET /api/v1/profile` returns `404` when no profile exists for the user.
- `PUT /api/v1/profile` creates a profile scoped to the authenticated user.
- `PUT /api/v1/profile` updates the same profile instead of creating a second row.
- A second user cannot read the first user's profile.
- Invalid currency returns `422`.

Validation:

```bash
cd backend
pytest tests/test_profile_api.py -v
ruff check app tests
```

Stop point:


Create request body:

```json
{
  "symbol": "VOO",
  "name": "Vanguard S&P 500 ETF",
  "exchange": "NYSEARCA",
  "currency": "USD",
  "asset_class": "ETF",
  "sector": "Broad Market",
  "country": "United States",
  "region": "North America",
  "quantity": "12.5",
  "average_cost": "418.23"
}
```

Response body:

```json
{
  "id": 1,
  "instrument": {
    "id": 1,
    "symbol": "VOO",
    "name": "Vanguard S&P 500 ETF",
    "exchange": "NYSEARCA",
    "currency": "USD",
    "asset_class": "ETF",
    "sector": "Broad Market",
    "country": "United States",
    "region": "North America"
  },
  "quantity": "12.5",
  "average_cost": "418.23",
  "created_at": "2026-06-04T00:00:00Z",
  "updated_at": "2026-06-04T00:00:00Z"
}
```

Implementation:

- Normalize `symbol`, `exchange`, and `currency` to uppercase.
- Treat blank optional instrument fields as `null`, except exchange which is normalized to an empty string for uniqueness.
- Require `quantity > 0` and `average_cost >= 0`.
- Create or reuse an instrument by normalized `symbol` and `exchange`.
- Scope all holding reads, updates, and deletes by authenticated `user_id`.
- Return `404` when a holding ID does not belong to the current user.
- Return `204` on successful delete.

Test cases:

- All holdings endpoints require auth.
- Creating a holding inserts or reuses an instrument.
- Listing holdings returns only the authenticated user's holdings.
- Getting another user's holding by ID returns `404`.
- Updating another user's holding by ID returns `404`.
- Deleting another user's holding by ID returns `404`.
- Invalid quantity or average cost returns `422`.
- Symbol and currency are normalized in responses.
