# M5 Implementation Plan — Transactions, Goal Projection, PWA Install, CSV Import

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Stop points gate each feature group for review.

## Context

M5 is the next unstarted milestone (`README.md:245`, `docs/architecture.md:481`). It bundles four features that turn Portfolius from a *current-state* dashboard into one that records history and projects forward: a **transactions log**, **goal projection**, **PWA install**, and **CSV import**.

The pivotal decision is the transactions architecture. Rather than a passive log, **transactions become the authoritative record of positions, and the existing `holdings` table becomes a derived read-model** recomputed (folded) from a user's transaction history per instrument. This is the long-run-correct choice for the project's stated principle — "keep portfolio math deterministic and testable" — because it unlocks weighted-average cost basis, realized gains, and the contribution/price history that M4 explicitly deferred, **while leaving the entire M2–M4 allocation / simulation / composition / assistant pipeline untouched** (they all read `holdings`, which keeps its shape). CSV import then naturally imports transactions, and goal projection consumes the current snapshot value plus new profile inputs.

Scope decisions: transactions = source of truth (holdings derived); goal projection = **both** a growth curve and a configurable target with progress; CSV import targets **transactions** (following the source-of-truth decision); all four features shipped in one sequenced doc with a stop point between each group.

## Goal

- **Transactions:** a full buy/sell ledger (date, quantity, price, fees) that is the source of truth; `holdings` is recomputed from it. New `/api/v1/transactions` CRUD and a Transactions page. Existing holdings CRUD becomes a thin wrapper over transactions so its API/UI keep working.
- **Goal projection:** a deterministic forward projection from the current portfolio value + recurring contributions + an assumed return over the profile's horizon, shown as a growth curve (conservative / expected / optimistic) against a configurable target with a progress + on-track readout.
- **PWA install:** the app is installable (manifest, maskable icons, service worker precaching the app shell, a custom install prompt), with financial/API data never cached.
- **CSV import:** import a transaction history (or a simple positions list) via client-side CSV parsing into a bulk transactions endpoint, with a per-row result report.

## Architecture

- **Backend stays the source of truth for math.** A new pure `fold_transactions(legs)` domain function (`domain/transactions.py`) replays one instrument's legs into `(quantity, average_cost, total_cost, realized_gain)` using weighted-average cost basis. A repository `recompute_holding(db, user_id, instrument_id)` materializes that fold into the derived `holdings` row (upsert, or delete when quantity hits 0). Every transaction write recomputes the affected position inside the same DB transaction and rejects invalid folds (e.g. a sell exceeding held quantity → HTTP 422).
- **Holdings pipeline unchanged.** `build_snapshot_for_user` → `list_holdings_for_user` → the M2/M3/M4 allocation, simulation, composition, and assistant tools all keep reading `holdings`. No allocation math changes.
- **Projection is a pure transform** (`domain/projection.py`) over the snapshot's `total_market_value` plus new profile fields; exposed through a lazily-fetched endpoint and rendered with a Recharts line/area chart.
- **PWA** via `vite-plugin-pwa` (generateSW / autoUpdate) precaching only the static app shell; API calls and auth are network-only.
- **CSV import** parses in the browser (no new multipart backend path; `apiRequest` stays JSON-only) and POSTs rows to a bulk transactions import endpoint that reuses the same instrument-resolution and fold logic as single creates.

## Tech Stack

FastAPI, SQLAlchemy 2.0, Alembic, pytest, Decimal math (backend). React, Vite, TypeScript, TanStack Query, Recharts, Vitest (frontend). **One new frontend dependency:** `vite-plugin-pwa` (+ its `workbox` transitive deps). Two new Alembic migrations (`0008`, `0009`). No new backend dependencies; CSV parsing is done client-side with a small hand-rolled parser (or a tiny dep only if justified during Step 8).

- Monte-Carlo / probabilistic projections. Projection is deterministic scenario bands, not a distribution.
- Profile intelligence, suggested tags, typo cleanup, dark mode (M6).

## Definition of Done

M5 is complete when:

- `fold_transactions` is pure, deterministic, and unit-tested (buys, sells, weighted-average cost basis, realized gain, insufficient-quantity error, ordering by `(trade_date, id)`) with no DB/network.
- Creating/editing/deleting a transaction recomputes the derived holding correctly; a sell (or a delete) that would drive quantity negative returns 422 and rolls back; a position hitting exactly 0 removes the holding row.
- `GET /api/v1/portfolio/breakdowns` and `POST /api/v1/portfolio/simulate` responses and the assistant tools are unchanged (regression tests pass) — the holdings-reading pipeline is untouched.
- The existing holdings API still behaves per its contract (create/list/update/delete), with the one intentional change that two adds of the same instrument now collapse into a single derived holding (test updated).
- The migration upgrades a populated DB so that post-migration derived holdings equal pre-migration holdings, and `uq_holdings_user_instrument` holds.
- The projection endpoint returns conservative/expected/optimistic yearly series from the current value + contributions + return over the horizon, plus a target-progress and on-track verdict; it is auth'd, user-scoped, and 404s without a profile. The dashboard renders it accessibly.
- The app passes an installability check (Lighthouse PWA / Chrome install), installs with correct name and maskable icons, and the service worker does not cache API/auth responses.
- CSV import parses a template file, previews rows, imports valid transactions, and reports per-row failures without a full-batch abort where partial success is safe.
- Backend and frontend lint, tests, and the production build pass. README and `docs/architecture.md` document all four features.

## Data Contracts

### Transaction

```text
GET    /api/v1/transactions            (optional ?instrument_id= or ?symbol=), ordered trade_date desc, id desc
POST   /api/v1/transactions            -> 201
GET    /api/v1/transactions/{id}       -> 404 for another user
PUT    /api/v1/transactions/{id}
DELETE /api/v1/transactions/{id}       -> 204
POST   /api/v1/transactions/import     -> bulk; per-row {imported | failed, reason}
```

`TransactionRequest`: `instrument_id | symbol` (exactly one, like `TradeLeg`), optional instrument metadata (same fields as `HoldingRequest`), `action: "buy"|"sell"`, `quantity` (>0), `price` (>=0), `fees` (>=0, default 0), `trade_date: date`, `notes?`. Decimals serialize to strings. Instrument resolution reuses `get_or_create_instrument` (rich payload) or `resolve_or_create_instrument` from `domain/simulation.py` (symbol-only). 422 on `InsufficientQuantityError`.

`TransactionResponse`: `id`, `instrument: InstrumentResponse` (reuse from `schemas/holdings.py`), `action`, `quantity`, `price`, `fees`, `currency`, `trade_date`, `notes`, `created_at`, `updated_at`.

### Projection

```text
GET /api/v1/portfolio/projection   (optional overrides: ?target=&contribution=&annual_return=&years=)
```

`ProjectionResponse` (decimals as strings): `base_currency`, `start_value`, `target_amount?`, `horizon_years`, `contribution_amount`, `contribution_frequency`, `annual_return_expected`, `series`: list of `{ year, conservative, expected, optimistic }`, `target_progress_percent?`, `on_track?: bool`, `target_reached_year?`. Growth uses periodic compounding at the profile's `investment_frequency` cadence; bands are expected ± a fixed spread (e.g. ±2 percentage points, documented in `domain/projection.py`). Horizon is mapped from `time_horizon` (`1-3→3`, `3-7→7`, `7-10→10`, `10+→15`, documented) unless `?years=` overrides.

### Profile (new fields, all nullable, decimals as strings)

`goal_target_amount`, `contribution_amount` (per `investment_frequency` period), `expected_annual_return` (percent). Added to `ProfileRequest`/`ProfileResponse` (`schemas/profile.py`), `upsert_profile` (`repositories/profiles.py`, using the `model_fields_set` guard pattern), and both profile forms.

## Step 1: Transaction Fold Math (pure)

Goal: replay a list of one instrument's legs into a position, purely.

Files: create `backend/app/domain/transactions.py`, `backend/tests/test_transactions.py`.

- `TransactionLeg` / `PositionState` frozen dataclasses (no SQLAlchemy import), `InsufficientQuantityError(ValueError)`, `sort_legs` (by `trade_date`, then `id`), `fold_transactions(legs) -> PositionState`.
- Weighted-average cost basis: a **buy** raises quantity and cost basis (fees capitalized); a **sell** reduces quantity and cost basis proportionally, leaves `average_cost` unchanged, and accrues `realized_gain = qty*(price-avg) - fees`; quantity reaching 0 resets `total_cost` to avoid Decimal residue. A sell exceeding held quantity raises `InsufficientQuantityError`.
- TDD first, mirroring `tests/test_simulation.py` style.

Test cases: single buy; two buys average correctly; buy→sell realized gain and unchanged avg cost; sell to exactly zero; oversell raises; out-of-order legs fold deterministically by `(trade_date, id)`; fees capitalized on buy / deducted on sell.

Validation: `cd backend && pytest tests/test_transactions.py -v && ruff check app tests`.

Stop point: fold passes pure unit tests before any DB layer depends on it.

## Implementation Notes

- **Keep the fold pure.** `fold_transactions` takes legs and returns a `PositionState`; the repository supplies legs and materializes the result. No allocation math is duplicated.
- **Do not touch the holdings read pipeline.** `list_holdings_for_user`, `build_snapshot_for_user`, `build_allocation_breakdowns`, `build_composition`, simulation, and the assistant tools stay byte-for-byte. Transactions only change how `holdings` rows are *written*.
- **The authoritative ledger rejects oversells** (422 + rollback), unlike simulation's `apply_sell`, which caps-and-warns for hypotheticals. That difference is intentional.
- **One derived holding per (user, instrument)** is the new invariant enforced by `uq_holdings_user_instrument`; the migration merges pre-existing duplicates. The one holdings test asserting two rows must be updated.
- **Single currency per instrument** carries over from M2–M4; mixed-currency legs for one instrument are out of scope.
- **Projection needs numeric inputs** because `time_horizon`/`investment_frequency` are non-numeric range strings; add the three numeric profile fields and derive horizon years from `time_horizon` via a documented map.
- **The service worker must never cache API/auth responses** — precache the static shell only.
- **CSV import stays JSON** (client-side parse → JSON bulk endpoint); do not add a multipart path to `apiRequest`.
- Use `Decimal` in backend math and serialize numbers as strings in all new contracts, matching M2–M4.
