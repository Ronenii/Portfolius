# M0 Implementation Plan

M0 is the walking skeleton. Its job is to prove that the app can run locally and deploy end-to-end:

```text
Browser -> React/Vite frontend -> FastAPI backend -> Supabase Postgres
```

This plan is designed for small controlled steps. Each step should be implemented, tested, and reviewed before moving to the next one.

## M0 Scope

Included:

- Create backend skeleton with FastAPI.
- Create frontend skeleton with React, Vite, TypeScript, and Tailwind.
- Add minimal database connectivity through SQLAlchemy.
- Add one Alembic migration for a tiny `app_health_checks` table or equivalent database probe.
- Add local environment examples.
- Add basic CI.
- Add Render and Vercel deployment configuration.
- Add a minimal deployed frontend that can call the backend health endpoint.

Excluded:

- Supabase magic-link UI.
- User profile wizard.
- Holdings CRUD.
- Market data.
- Portfolio calculations.
- AI assistant.
- Charts.

## Definition of Done

M0 is complete when:

- `GET /healthz` returns OK locally and in Render.
- Backend can connect to Postgres locally and in Supabase.
- Alembic migrations run from a clean database.
- Frontend runs locally and displays backend health status.
- Frontend production build succeeds.
- CI runs backend and frontend checks.
- README setup instructions match the actual commands.

Goal: make the current repo state explicit before code generation starts.

Actions:

- Add `docs/architecture.md`.

- Do not scaffold backend or frontend yet.

Validation:

```bash
git status --short
```

Stop point:

- Review the architecture and M0 plan.
- Decide whether to proceed to Step 1.

## Step 1: Backend Skeleton

Goal: create the smallest FastAPI app that starts cleanly.

Files to add:

```text
backend/
├── app/
│   ├── __init__.py
│   ├── main.py
│   └── api/v1/health.py
├── tests/
│   └── test_health.py
├── pyproject.toml
└── .env.example
```

Implementation:

- Add FastAPI app factory or simple `app` in `app/main.py`.
- Add `GET /healthz`.
- Add pytest with a health endpoint test.
- Add `ruff` formatting/lint config.

Validation:

```bash
cd backend
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
pytest
ruff check .
```

Stop point:

- Confirm backend skeleton and test style before adding database code.

## Step 2: Backend Database Skeleton

Goal: prove backend-to-Postgres connectivity without product data.

Files to add or update:

```text
backend/
├── alembic/

├── app/core/config.py
├── app/data/database.py
```

Stop point:

- Confirm frontend displays backend health.


```text
.github/workflows/ci.yml
```

Implementation:

- Backend job: install dependencies, run `ruff check .`, run `pytest`.

Validation:

```bash

```

Stop point:

- Review CI commands against the actual package scripts.

## Step 6: Deployment Configuration

Goal: configure free-tier deployment without adding product features.

Files to add:

```text
backend/render.yaml
frontend/vercel.json
```

Implementation:

- Render runs FastAPI through uvicorn.
- Render pre-deploy runs Alembic migration if supported by the selected setup.
- Vercel builds the Vite app.
- Required env vars are documented but not committed with values.

Validation:

- Render deploy succeeds.
- Vercel deploy succeeds.
- Deployed frontend can call deployed backend `/healthz`.

Stop point:

- M0 is done. Do not continue into M1 without explicit approval.

## Change Control

For this project, implementation should follow this loop:

1. Pick exactly one step.
2. Implement only that step.
3. Run that step's validation.
4. Summarize changed files and validation results.
5. Wait for approval before starting the next step.

This is intentionally slower than building the whole scaffold at once. The point is to keep architecture, code shape, and project preferences visible while the foundation is still easy to change.
