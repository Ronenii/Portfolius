# M3 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add portfolio simulation (what-if buy/sell scenarios) and an AI assistant grounded in the user's profile goals and current portfolio context. Enrich the profile so a user can describe their interests and goals at setup time, then let the assistant reason over that context and run real before/after/delta simulations through LLM tool-calling.

**Architecture:** The backend stays the source of truth for all portfolio math. Simulation introduces no new persistence and no new math: it is a pure, in-memory transform over the existing deterministic M2 snapshot/breakdown pipeline. The assistant talks to a Groq-compatible LLM behind a local, mockable integration interface, receives only summarized portfolio context (never raw secrets), and grounds rebalancing analysis by calling backend tools (`simulate_trades`, `get_portfolio_breakdowns`) rather than guessing numbers. Conversations are persisted and user-scoped. The assistant is educational analysis, not personalized financial advice. Responses return as complete messages (no streaming in M3).

**Tech Stack:** FastAPI, SQLAlchemy, Alembic, httpx, pytest, Groq (OpenAI-compatible Chat Completions API with tool-calling), React, Vite, TypeScript, TanStack Query, Vitest.

## Definition of Done

M3 is complete when:

- Alembic upgrades a clean database to add the new profile columns and the `conversations` and `messages` tables with their constraints and indexes.
- New profile fields are optional; existing M1/M2 profiles remain valid and round-trip through the API unchanged.
- The profile wizard captures risk tolerance, interest tags, sectors to avoid, and a free-text goals note, and persists them.
- `apply_trades` and `diff_breakdowns` are pure, deterministic, and covered by unit tests without network or database access.
- `POST /api/v1/portfolio/simulate` is user-scoped, returns `current`/`simulated`/`delta`/`warnings`, defaults missing leg prices to the latest stored close, validates sells against held quantity, and returns warnings (not errors) for unpriced new instruments and over-sells.
- All assistant and simulate endpoints return `401` without auth and operate only on the authenticated user's data.
- The LLM client is isolated behind a protocol; no test hits the network or a real LLM provider.
- The assistant context contains summarized profile goals and allocation summary only — tests assert it never includes raw secrets or unrelated user metadata.
- The assistant tool-call loop can call `simulate_trades` and `get_portfolio_breakdowns`, feed real results back to the model, and return a final grounded reply.
- Conversations and messages persist per user, survive reload, and are listable and retrievable through the API.
- The assistant carries an educational-only system guardrail.
- The frontend renders the simulation panel and the assistant chat, including loading, empty, error, and missing-LLM-config states.
- Backend and frontend lint, tests, and the production build pass.
- README, `docs/architecture.md`, and `.env.example` document the LLM configuration and assistant/simulation behavior.

## Data Contracts

### Profile goal fields

The single `profiles` row gains four optional columns:

- `risk_tolerance`: one of `"conservative"`, `"balanced"`, `"aggressive"`, or `null`.
- `interest_tags`: JSON array of lowercase slugs drawn from a known vocabulary, defaults to `[]`.
- `excluded_sectors`: JSON array of lowercase slugs the user wants to avoid, defaults to `[]`.
- `goals_note`: free text up to 1000 characters, or `null`.

Suggested vocabularies (the wizard renders these as checkboxes; the API accepts any of them and ignores unknown values defensively):

```text
INTEREST_TAGS     = ["dividends", "growth", "value", "technology", "esg",
                     "bonds", "real_estate", "emerging_markets",
                     "broad_market", "income"]
EXCLUDABLE_SECTORS = ["tobacco", "weapons", "fossil_fuels", "gambling",
                      "crypto", "alcohol"]
```

`PUT /api/v1/profile` request and `GET /api/v1/profile` response both carry these fields. They are optional in the request; omitted fields keep their current stored value on update.

```json
{
  "display_name": "Ronen",
  "base_currency": "USD",
  "time_horizon": "10+ years",
  "investment_frequency": "monthly",
  "risk_tolerance": "balanced",
  "interest_tags": ["dividends", "technology", "broad_market"],
  "excluded_sectors": ["tobacco", "crypto"],
  "goals_note": "Long-term growth for a house down payment in ~7 years. Prefer low-fee ETFs."
}
```

### Simulate request and response

`POST /api/v1/portfolio/simulate` accepts a basket of legs. Each leg identifies an instrument by `instrument_id` (preferred, for already-known instruments) or `symbol` (resolved via M2 instrument lookup), an `action`, a positive `quantity`, and an optional `price` that defaults to the latest stored close.

```json
{
  "legs": [
    { "instrument_id": 12, "action": "sell", "quantity": "10" },
    { "symbol": "VXUS", "action": "buy", "quantity": "5" },
    { "symbol": "BND", "action": "buy", "quantity": "3", "price": "72.50" }
  ]
}
```

Response reuses the M2 `PortfolioBreakdowns` shape for `current` and `simulated`, adds a flat `delta` list, and surfaces non-fatal `warnings`:

```json
{
  "current": { "instrument": [], "asset_class": [], "sector": [], "country": [],
               "region": [], "currency": [], "unpriced_holding_count": 0 },
  "simulated": { "instrument": [], "asset_class": [], "sector": [], "country": [],
                 "region": [], "currency": [], "unpriced_holding_count": 0 },
  "delta": [
    {
      "dimension": "asset_class",
      "label": "ETF",
      "currency": "USD",
      "percent_before": "62.00",
      "percent_after": "58.40",
      "percent_change": "-3.60"
    }
  ],
  "warnings": [
    "BND has no stored price; using the price supplied in the request leg.",
    "Sell of 10 AAPL exceeds the held quantity of 6; capped at 6."
  ]
}
```

Behavior:

- Buying an instrument not yet held resolves its metadata and latest price through the M2 instrument lookup. Without sector/country/region the holding cannot be allocated meaningfully, so the response includes a warning and the holding contributes only to `instrument`/`currency` dimensions.
- Sells are validated against the held quantity. The product does not model shorting; an over-sell is capped at the held quantity with a warning rather than rejected.
- Legs with no resolvable price and no supplied `price` are excluded from market-value math with a warning, exactly as unpriced holdings are in M2.
- The endpoint uses POST because the input is a structured basket even though the operation is non-mutating. It is user-scoped like the other portfolio endpoints. Nothing is persisted.
- `delta` rows are emitted for every dimension/label present in either `current` or `simulated`. A label that appears only after the trade has `percent_before = "0.00"`; one that disappears has `percent_after = "0.00"`.

### Conversation and message models

`conversations`:

- `id`: integer primary key.
- `user_id`: Supabase user ID, required.
- `title`: short text derived from the first user message, required.
- `created_at`, `updated_at`: timestamps, required.

`messages`:

- `id`: integer primary key.
- `conversation_id`: foreign key to `conversations.id`, required, cascade delete.
- `role`: one of `"user"`, `"assistant"` (tool exchanges are summarized, not persisted as separate rows in M3), required.
- `content`: text, required.
- `created_at`: timestamp, required.

Constraints and indexes:

- Index: `conversations.user_id`.
- Index: `messages.conversation_id`, `messages.created_at`.
- `conversations.messages` relationship with cascade delete-orphan.

### Assistant request and response

`POST /api/v1/assistant/messages`:

```json
{ "conversation_id": 7, "message": "How would selling 10 AAPL and buying VXUS shift my regional exposure?" }
```

- `conversation_id` is optional. When omitted, a new conversation is created and its `id` and derived `title` are returned.
- Response:

```json
{
  "conversation_id": 7,
  "title": "Rebalancing AAPL into VXUS",
  "reply": {
    "role": "assistant",
    "content": "Selling 10 AAPL and buying 5 VXUS would move your North America exposure from 78% to 71% ...",
    "created_at": "2026-06-08T12:00:00Z"
  },
  "used_tools": ["simulate_trades"]
}
```

`GET /api/v1/assistant/conversations` returns a user-scoped list of `{ id, title, created_at, updated_at }` ordered by `updated_at` descending.

`GET /api/v1/assistant/conversations/{conversation_id}` returns the conversation plus its ordered messages, scoped to the authenticated user (`404` for another user's conversation).

### LLM tools

The assistant exposes two tools to the model. Both execute the same user-scoped domain functions used by the REST endpoints, so the model reasons over identical numbers.

```text
get_portfolio_breakdowns()
  -> the user's current PortfolioBreakdowns (summarized to percentages and top rows)

simulate_trades(legs: [{ symbol|instrument_id, action, quantity, price? }])
  -> the simulate response: current, simulated, delta, warnings (summarized)
```

## Step 3: Simulation Math

Goal: compute hypothetical before/after/delta allocations as a pure transform over the M2 pipeline.

Files:

- Create: `backend/app/domain/simulation.py`
- Create: `backend/app/schemas/simulation.py`
- Create: `backend/tests/test_simulation.py`

Implementation:

- Define `TradeLeg` (Pydantic): `instrument_id: int | None`, `symbol: str | None`, `action: Literal["buy","sell"]`, `quantity: Decimal` (> 0), `price: Decimal | None`. Validate that exactly one of `instrument_id`/`symbol` is provided and `quantity > 0`.
- Implement `apply_trades(holdings, latest_prices, legs, *, resolve_instrument, resolve_price)` as a pure function that returns a hypothetical `(holdings, latest_prices, warnings)`:
  - Work on copies; never mutate the input holdings/prices.
  - For a `buy` of a held instrument, increase quantity; for a new instrument, create a synthetic holding using the resolved instrument metadata.
  - For a `sell`, decrease quantity, capping at the held quantity and emitting a warning on over-sell. A position reduced to zero is removed.
  - `resolve_instrument` and `resolve_price` are injected callables so the function stays pure and testable without a database; the API layer supplies DB-backed implementations.
  - Use the leg `price` when given; otherwise the resolved latest close; otherwise mark the holding unpriced and warn.
  - Use `Decimal` throughout.
- Implement `diff_breakdowns(before: PortfolioBreakdowns, after: PortfolioBreakdowns) -> list[AllocationDelta]`:
  - Emit one row per `(dimension, label, currency)` present in either side.
  - `percent_before` / `percent_after` default to `Decimal("0.00")` when absent; `percent_change = percent_after - percent_before`.
  - Sort by dimension order, then by absolute `percent_change` descending.
- Define `SimulationResponse` schema: `current`, `simulated` (`PortfolioBreakdowns`), `delta` (`list[AllocationDelta]`), `warnings` (`list[str]`), serializing decimals as strings like the M2 schemas.

Test cases:

- Selling part of a held position reduces its market value and shifts percentages; totals still sum to 100 per currency.
- Selling the entire position removes it from the instrument breakdown.
- Over-selling caps at the held quantity and emits a warning.
- Buying more of a held instrument increases its allocation.
- Buying a new instrument with resolved metadata adds rows across `instrument` and its `asset_class`/`sector`/`country`/`region`.
- Buying a new instrument with no resolvable price excludes it from market-value math and warns.
- `apply_trades` does not mutate the input holdings or prices.
- `diff_breakdowns` emits before-only and after-only labels with the correct zero baseline.

## Step 8: Assistant Domain and Tool-Call Loop

- All tool executors are user-scoped; a tool can never read another user's data.

## Implementation Notes

- Keep simulation pure: `apply_trades` and `diff_breakdowns` take injected resolvers and never touch FastAPI, the database, or the network directly. The API layer supplies DB-backed resolvers.
- Reuse the M2 pipeline verbatim. Simulation must not introduce a second copy of snapshot or allocation math.
- Use `Decimal` in all backend math and serialize numbers as strings in API contracts, matching M2.
- Never send raw holdings, secrets, tokens, or user IDs to the LLM. The assistant receives only summarized context, per the architecture's security boundaries.
- Keep the LLM behind the `LlmClient` protocol; no test may hit a real provider. Use fakes or mocked transports.
- Cap the tool-call loop iterations to prevent runaway provider usage on the free tier.
- Frame the assistant as educational analysis, not personalized financial advice, in the system prompt and the UI.
- Do not persist simulation scenarios or add multiple named portfolios in M3; both are deliberately deferred.
