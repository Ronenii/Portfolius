# M4 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add allocation exploration to the dashboard. Let a user inspect *what's inside* any allocation slice (a composition drill-down — e.g. open the 62% ETF row to see VOO, VXUS, IXC and their weights) and view each breakdown dimension through their preferred chart type (bar/column, pie/donut, or table-first). No change to the underlying allocation math.

**Architecture:** The backend stays the source of truth for the math. Composition is a new, pure, in-memory transform over the existing M2 snapshot pipeline: given a dimension and a selected key, it returns the priced child instruments inside that slice with two percentages — percent of the parent slice and percent of the whole portfolio. It is exposed through a dedicated, lazily-fetched endpoint so the existing `PortfolioBreakdowns` contract (which the simulation diff and assistant tool both consume) stays untouched. The frontend adds a chart-type selector persisted to `localStorage` (mirroring the terminal-mode pattern) and a drill-down popover triggered by hover and by keyboard (focus/Enter). The dense allocation table remains the canonical, accessible view. No line charts: a single current snapshot is not time-series data.

**Tech Stack:** FastAPI, SQLAlchemy, pytest, React, Vite, TypeScript, TanStack Query, Recharts, Vitest. No new dependencies, no Alembic migration (M4 adds no persisted data).

## Data Contracts

### Composition request

`GET /api/v1/portfolio/breakdowns/{dimension}/{key}/composition`

- `dimension`: one of `asset_class`, `sector`, `country`, `region`, `currency`, `instrument`. An unknown dimension is rejected.
- `key`: the allocation row `label` to drill into (e.g. `ETF`, `Technology`, `North America`, `USD`). URL-encoded. An unknown-but-valid key returns an empty child list with zeroed totals, not an error.
- Auth required; user-scoped exactly like the other portfolio routes.

The `instrument` dimension is a degenerate case: a slice keyed by a symbol contains exactly that one instrument at `percent_of_parent = 100`. It is accepted for uniformity.

### Composition response

Reuses the existing decimal-as-string serialization convention.

```json
{
  "dimension": "asset_class",
  "key": "ETF",
  "currency": "USD",
  "market_value": "62000.00",
  "percent_of_portfolio": "62.00",
  "children": [
    {
      "instrument_id": 12,
      "symbol": "VOO",
      "name": "Vanguard S&P 500 ETF",
      "currency": "USD",
      "market_value": "30000.00",
      "holding_count": 1,
      "percent_of_parent": "48.39",
      "percent_of_portfolio": "30.00"
    },
    {
      "instrument_id": 7,
      "symbol": "VXUS",
      "name": "Vanguard Total International Stock ETF",
      "currency": "USD",
      "market_value": "27000.00",
      "holding_count": 1,
      "percent_of_parent": "43.55",
      "percent_of_portfolio": "27.00"
    }
  ],
  "unpriced_holding_count": 0
}
```

Behavior:

- `children` lists priced holdings whose value for `dimension` equals `key` (and, for non-`currency` dimensions, whose currency matches the slice's reported `currency`), sorted by `market_value` descending then `symbol`.
- `percent_of_parent` is the child's market value over the slice total; `percent_of_portfolio` is over the per-currency portfolio total. Both use the same `percent_of` math as M2 and serialize as strings.
- A slice may span multiple currencies (e.g. an `ETF` slice with USD and EUR holdings). Like M2 breakdowns, percentages are computed per currency. The endpoint resolves the parent slice for the currency that owns the requested `(dimension, key)` row; when a label exists in more than one currency, the response is scoped to one currency row at a time, consistent with how `AllocationRow` already keys on `(currency, label)`.
- `Unclassified` is a valid key: holdings with a null sector/country/region/asset_class group under `Unclassified` exactly as in `build_allocation_breakdowns`.
- Unpriced holdings never appear in `children` and are reported via `unpriced_holding_count`, matching M2.
- Nothing is persisted; this is a pure read.

## Step 1: Composition Math

Goal: compute the child instruments inside a selected allocation slice as a pure transform over the M2 snapshot.

Files:

- Modify: `backend/app/domain/allocation.py`
- Modify: `backend/app/schemas/portfolio.py`
- Create: `backend/tests/test_composition.py`

Implementation:

- Add `CompositionRow` and `CompositionResponse` to `schemas/portfolio.py`:
  - `CompositionRow`: `instrument_id: int`, `symbol: str`, `name: str`, `currency: str`, `market_value: Decimal`, `holding_count: int`, `percent_of_parent: Decimal`, `percent_of_portfolio: Decimal`, with a `field_serializer` rendering the decimals as strings.
  - `CompositionResponse`: `dimension: str`, `key: str`, `currency: str`, `market_value: Decimal`, `percent_of_portfolio: Decimal`, `children: list[CompositionRow]`, `unpriced_holding_count: int`, with the same decimal serialization.
- Define the canonical dimension set once (e.g. `COMPOSITION_DIMENSIONS`) reusing the same `label_for` mappers `build_allocation_breakdowns` already uses (`instrument`, `asset_class`, `sector`, `country`, `region`, `currency`), so composition labels match breakdown labels exactly (including `Unclassified`).
- Add `build_composition(snapshot, dimension, key, *, currency=None) -> CompositionResponse`:
  - Filter to priced holdings; compute `unpriced_holding_count` like `build_allocation_breakdowns`.
  - Select holdings whose `label_for(holding) == key`. When the dimension is not `currency`, restrict to the matching `currency` (defaulting to the currency of the first matching holding when not supplied) so totals are single-currency, mirroring the `(currency, label)` keying of `AllocationRow`.
  - Per matching holding, accumulate market value and holding count by instrument (so a doubled position collapses to one child row with `holding_count = 2`).
  - Compute the per-currency portfolio total for `percent_of_portfolio` and the slice total for `percent_of_parent`, reusing `percent_of`.
  - Return rows sorted by `market_value` desc, then `symbol`. An unknown key yields empty `children`, `market_value = 0`, `percent_of_portfolio = 0`.
- Keep the function pure: it takes a `PortfolioSnapshot` and returns a `CompositionResponse`; no DB, FastAPI, or network access.

Test cases:

- Drilling into an `asset_class` slice returns its instruments with `percent_of_parent` summing to ~100 and `percent_of_portfolio` matching the M2 instrument breakdown.
- A doubled holding (two lots of the same instrument) collapses into one child with `holding_count = 2` and combined value.
- Drilling into `Unclassified` (null sector/region) returns the unclassified holdings.
- An unknown key returns empty children and zeroed totals without raising.
- The `instrument` dimension returns a single child at `percent_of_parent = 100`.
- Unpriced holdings are excluded from children and counted in `unpriced_holding_count`.
- A slice with holdings in two currencies returns one currency's members per call, scoped to the requested currency.
- `build_composition` does not mutate the snapshot.

## Implementation Notes

- Keep composition pure: `build_composition` takes a snapshot and returns a `CompositionResponse`; the API layer supplies the snapshot via `build_snapshot_for_user`. No second copy of allocation math.
- Reuse the M2 `label_for` mappers and `percent_of` so composition labels and percentages match the breakdowns exactly, including `Unclassified` and the `(currency, label)` keying.
- Do not modify `PortfolioBreakdowns`/`AllocationRow`. The simulation diff and the assistant `get_portfolio_breakdowns` tool depend on that shape; M4 adds a sibling contract instead.
- Use `Decimal` in backend math and serialize numbers as strings in API contracts, matching M2/M3.
- The drill-down must be keyboard-accessible and expose the same data through the table; never make composition hover-only.
- No line charts in M4 — a single current snapshot is not time-series data. Defer trend visualizations until a milestone adds history.
- Chart-type preference is client-only (`localStorage`), following the terminal-mode pattern; do not add a server-side preference store.
